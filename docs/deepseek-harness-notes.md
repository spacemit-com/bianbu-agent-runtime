## 2026-10-19 — model reasoning effort interface

- Request: Add `off` / `low` / `high` / `max` reasoning effort to an Expert's model selection, default `low`, editable in the Expert editor.
- Harness revision: `d743267388641bc76f17c45ce8b4c231aed1d32c`
- Source evidence: `packages/llm/llm-deepseek/src/model-info.ts` (`REASONING_EFFORTS`, `OFF_ONLY_REASONING_EFFORTS`), `packages/llm/llm-deepseek/src/config.ts` (`reasoningEffort`, default `high`), `packages/llm/llm-deepseek/src/serialize.ts` (`thinking`, `output_config.effort`), `packages/llm/llm-pi-ai/src/adapter.ts` (`reasoningInfo`), pi-ai `dist/api/openai-completions.js` (`thinkingFormat === "deepseek"`, default openai-completions branch), and `packages/llm/llm-pi-ai/tests/adapter.spec.ts` ("dispatches the compat-switched dialect on a declared route").
- Observed contract: the canonical levels are `off`, `low`, `high`, and `max`; a thinking-disabled connection exposes `off` only. Harness's DeepSeek Messages route serializes `thinking: {type: "disabled"}` plus no effort for `off`, and `thinking: {type: "enabled"}` plus `output_config.effort` otherwise. Its pi-ai OpenAI-compatible DeepSeek dialect instead sends `thinking` beside `reasoning_effort`; the plain OpenAI-compatible branch sends `reasoning_effort` and omits it for `off`. Harness's configured default is `high`, and its pi-ai adapter omits `reasoning` metadata entirely for a model that declares no reasoning capability.
- Target decision: Runtime stores `model.effort` in `agent.yaml`, forwards it through the resolved `OpenAICompatibleModel`, and defaults an omitted value to `low` as requested (a deliberate deviation from Harness's `high`). DeepSeek's OpenAI-compatible route is detected from the provider id or a `deepseek.com` base URL; `off` sends `thinking: {type: "disabled"}`, other levels send `reasoning_effort` with `thinking: {type: "enabled"}`, and other endpoints use the plain OpenAI spelling without `thinking`. PATCH that omits effort preserves the stored value. Auxiliary Session-title requests are forced to `low`.
- Verification: `tests/sdk/test_default_engine.py`, `tests/sdk/api/test_agents.py`, `tests/sdk/api/test_contracts.py`, `tests/sdk/agents/test_manifest.py`, `tests/sdk/test_sdk_models.py`, `tests/sdk/test_cli.py`, `tests/sdk/test_session_titles.py`, `tests/sdk/skills/test_expert_creator_skill.py`, and `tests/sdk/console/test_browser_contract.py` cover the wire payloads, persistence, validation, API defaulting/PATCH preservation, CLI and Skill creation, title isolation, and the Expert-editor round trip. ## 2026-10-20 — session title generation

- Request: Explain what Session titles are derived from using DeepSeek Harness as the reference, then make the title a log-only event that is visible, with its request context, in Trajectory.
- Harness revision: `d743267388641bc76f17c45ce8b4c231aed1d32c`.
- Source evidence: `packages/session/session-title/src/index.ts` (`onUserMessage`, `onRequestHeader`, `ensureFallback`, `appendFallback`, `collectSessionTitleMessages`, `titleProjectionDefinition`), `packages/session/session-title/src/normalize.ts` (`normalizeSessionTitle`, `fallbackSessionTitle`), `packages/session/session-title-first-prompt-llm/src/index.ts` (`systemPrompt`, `frameMessages`, `titleFromOutput`, `titleFromResponse`), `packages/session/session-title-llm/src/index.ts`, `packages/experimental/session-title-all-prompts-llm/src/index.ts`, `packages/bundle/base/cordis.patch.yml` (shipped `fallbackMaxWords: 5`, `fallbackMaxBytes: 40`, `maxTitleBytes: 80`, `targetWords: 5`, `targetCjkCharacters: 10`), plus the `session-title` and `session-title-first-prompt-llm` tests.
- Observed contract: Harness treats the title as log-only durable state folded from `session/title` events, with three sources ordered newest-wins: deterministic fallback, provider, explicit user rename. Eligibility is any `user/message` whose `source.kind === 'user'` and whose joined text blocks are non-empty after normalization. The fallback is the first eligible message's leading words capped by `fallbackMaxWords`/`fallbackMaxBytes`, appended immediately so a new Session is never untitled. The shipped provider (`first-prompt`) runs one auxiliary model call after the first eligible message, only for a fresh session with no parent and no title, and only once the exact main-request route is logged in `request/header`; later prompts, forks, and user renames never trigger it automatically, and `refresh()` is the explicit retry. The model request is a fixed English system instruction plus a JSON array `[{"seq":"<user/message seq>","text":"<text>"}]`; the instruction requires plain text, one line, no quotes/prefix/Markdown/XML/control codes or code, the message language, about `targetWords` words or `targetCjkCharacters` CJK characters, and a short best-effort title when the message names little. Output is the first non-empty line with whole-line asterisk emphasis stripped, then normalized (control/OSC/CSI/bidi removal, whitespace collapse, UTF-8-safe truncation to `maxTitleBytes`). The route inherits the logged main request unless `provider`/`model` are both overridden, reasoning effort is the route's least supported level, `maxOutputTokens` is a runaway ceiling rather than a length target, and title work never enters the main request or delays the response. `all-prompts` (experimental) retitles after every new prompt and passes `currentTitle` so an adequate provider-sourced title can be returned unchanged.
- Target decision: Runtime mirrors the log-only shape rather than Harness's provider-selection details. `POST /{session_id}/generate-title` writes a durable fallback `session/title` event immediately, then a detached task writes `session/title/request` (the exact system prompt and JSON input) before dispatch, calls the Agent's model through the Worker RPC operation `title.generate` (Worker-local callers generate in process), and appends `session/title/route` once the provider/model is resolved. A provider `session/title` event supersedes the fallback. Titles never create a Run, never take a concurrency slot, never wait for another Run, and never invoke any Hook. The title model still uses the existing bounded auxiliary call: 4096-byte input cap, 64-token output cap, 60s timeout, `reasoning_effort=low`, one-line parsing, and fallback on any `SessionTitleError`/timeout. User renames write `session/title` with `source.kind=user`, and an in-flight provider revision cannot overwrite them. The event stream thus has exactly two input kinds: Run events (`run_id` set) and Session-level title work (`run_id=null`, types `session/title`, `session/title/request`, `session/title/route`); Trajectory renders the latter as its own `title` unit with the request context and route, while Chat hides title state entirely. The Session list carries the folded title in its projection row, so listing stays a zero-I/O read; a cold single-Session read folds the transcript.
- Verification: `tests/sdk/api/test_sessions.py` (log-only, no Run, no Hooks, trajectory visibility, late revision, rename pinning, pending title never blocks a prompt), `tests/sdk/test_session_projection.py` (title and route survive restart, list row title), `tests/sdk/test_run_model_deadlines.py`, `tests/sdk/console/test_browser_contract.py` (title/Run projection), `tests/sdk/test_session_titles.py`, and `tests/runtime/test_worker_rpc.py`.

## 2026-10-28 — image input capability detection

- Request: Determine how DeepSeek Harness decides whether a model can read images, because Runtime reports `MODEL_DOES_NOT_SUPPORT_IMAGES` for `deepseek-flash` while the same endpoint demonstrably accepts images.
- Harness revision: `d743267388641bc76f17c45ce8b4c231aed1d32c` (clean working tree).
- Source evidence: `packages/llm/llm/src/types.ts` (`LlmModelInfo.inputModalities`, `LlmResolvedModelInfo`), `packages/llm/llm-deepseek/src/model-info.ts` (`catalogModelInfo`, `modelInfo`), `packages/llm/llm-deepseek/src/models.ts` (`DEFAULT_MODELS`), `packages/llm/llm-deepseek/src/config.ts` (`resolveModels`, `inputModalities` validation), `packages/llm/llm-deepseek/src/images.ts` (`prepareImages`), `packages/llm/llm-deepseek-api-key/src/index.ts` (`discoverModels`), `packages/llm/llm-pi-ai/src/discovery.ts` (`readListing`), `packages/llm/llm-pi-ai/src/catalog.ts` (`input: declaredInput(entry.input) ?? base?.input ?? [...request.defaultInput]`), `packages/llm/llm/src/index.ts` (`projectImagesForTextModel` guard), `packages/acp/acp/src/content.ts` (`assertImageRoute`, `supportsAcpImagePrompts`), `packages/api/session-controller/src/commands.ts` (prompt admission), `packages/subagent/subagent/src/manager.ts` (`assertImageCapable`), `docs/user/guide/providers.md` (Image input), tests `packages/acp/acp/tests/content.spec.ts` and `packages/llm/llm-pi-ai/tests/discovery.spec.ts`.
- Observed contract: capability is a **declared** `inputModalities` field, never inferred from the model name or model id; there is no name/VL/vision heuristic anywhere in `packages/llm`. Three declaration sources, in order: an explicit per-model `inputModalities`/`input` config override; the installed catalog entry (`DEFAULT_MODELS` for the direct DeepSeek adapter, pi-ai's catalog for pi-ai routes); then the route default (`defaultInput`, defaulting to `[text]`; the DeepSeek adapter instead defaults an omitted field to `['text']` and rejects an empty list). Discovery does not probe inference endpoints — the DeepSeek adapter's `discoverModels` merely re-publishes its configured catalog, and pi-ai's `readListing` extracts only id/name/context/output limits, never modalities. `LlmModelInfo.inputModalities` being `undefined` means *unknown*; an array without `image` is an explicit negative. Downstream surfaces disagree on what `undefined` means: llm core and session-controller/subagent admission treat unknown as permissive (images pass through, or are projected to text), while ACP `assertImageRoute` and the DeepSeek adapter's `prepareImages` require `includes('image') === true` and reject unknown. `modelInfo()` converts any uncatalogued model to explicit text-only with the stated rationale that declaring unverified image support would persist input the endpoint may reject on later turns. `deepseek-flash` is declared `['text','image']` in `DEFAULT_MODELS`; `deepseek-v4-pro` declares nothing and therefore resolves text-only.
- Target decision: Runtime adopted Harness's *declaration* model instead of its name heuristics. `bianbu_agent/models/vision.py` now exposes a three-valued `ImageSupport` (`SUPPORTED`/`UNSUPPORTED`/`UNKNOWN`) and deletes the `_IMAGE_MODEL_PATTERNS` regex table entirely. Resolution order mirrors Harness: an explicit `capability-vision` binding wins (equivalent to a per-model `inputModalities` override), then an exact-alias reviewed catalog `_DECLARED_IMAGE_MODELS`, then `UNKNOWN`. Exact alias only, matching `model_catalog.py`'s stated rule that unreviewed versions are not inferred from a prefix. Declarations for `deepseek-flash`, `deepseek-v4-flash`, `deepseek-v4-flash-vision-exp`, `deepseek-chat` and `deepseek-reasoner` were verified against `api.deepseek.com` on 2026-10-28 by comparing `prompt_tokens` with and without an image (234 vs 11); `deepseek-v4-pro` is the recorded explicit negative because it accepts the block and silently discards it.
- Deliberate deviations: (1) Harness ships a catalog only for its own two providers and publishes it through `discoverModels`; Runtime faces arbitrary user-configured OpenAI-compatible endpoints, so the catalog is a reviewed exact-alias table plus the pre-existing operator binding, and `/v1/models` discovery stays untouched because Harness's `readListing` also ignores modalities. (2) Harness is split on `undefined` — session-controller/subagent admission treat it as permissive while ACP `assertImageRoute` and DeepSeek `prepareImages` require `=== true`. Runtime takes the permissive reading on the *warning* path (`/vision` reports `available: true, state: unknown`) and adds a check Harness has no equivalent for: `read_image` compares the returned `prompt_tokens` against a text-only bound and reports `image_delivered: false` when a route accepted the block but discarded it. That closes the exact failure mode `deepseek-v4-pro` exhibits, where no provider error ever surfaces.
- Follow-up (same topic): the operator removed the local-endpoint gate in `read_image`. `_vision_payload_allowed`, `REMOTE_IMAGE_BLOCKED` and its copy are deleted; a remote vision Provider now receives image bytes like a loopback one, and only the `question` text still goes through `scan_text`. The rationale is that the DLP media rule exists to stop unscanned content leaving through paths nobody chose, while `read_image` is an explicit, operator-selected model call — the shipped `custom:bibit` provider could not read images at all otherwise. `docs/security-plugin.md` records `read_image` as the stated exception rather than silently diverging from the fail-closed rule.
- Verification: `tests/sdk/api/test_session_attachments.py` — `test_image_tool_sends_to_a_remote_vision_model`, `test_image_support_comes_from_declarations_not_name_shapes`, `test_an_explicitly_text_only_model_warns_but_still_stores_the_image`, `test_an_undeclared_model_is_unknown_and_keeps_the_image_affordance`, `test_an_unknown_model_is_judged_by_what_the_route_actually_did` (delivered/refused/unreported). Full `tests/sdk` run: 2160 passed, 3 pre-existing failures reproduced on the unmodified baseline (`test_image_tool_masks_the_question_for_a_local_vision_model`, `test_memory_hook_injects_context_only_for_agents_that_select_it`, `test_bundled_hooks_run_from_installed_plugin_members`, `test_title_request_masks_pii_before_the_provider_sees_it` — all assert a `PII` placeholder the installed securityd no longer emits). Live endpoint re-check after the change: `deepseek-flash` returns a real description with `image_delivered: true`; `deepseek-v4-pro` is refused before dispatch.
